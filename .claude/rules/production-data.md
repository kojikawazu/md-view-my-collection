# 本番データの保護

**本番データを壊す事故は、悪意ではなく「接続先を間違えたまま普段どおりの操作をした」ときに起きる。** 本ルールは、本番を書き換え得るすべての経路に共通の下限を定める。

> **本ルールの起点**: 姉妹プロジェクト `youtube-my-collection` で、E2E / IT のテスト DB 接続先が本番 Supabase を指し、seed の `deleteMany()` により**本番データが全削除される事故**が発生した（kojikawazu/youtube-my-collection#175）。原因は `process.env.DATABASE_URL ?? ローカル既定` というフォールバック。`@prisma/client` の import 時点で `.env` が `process.env` に読み込まれるため、この書き方は **`.env` の本番 URL を拾う**。「未設定なら安全側」に見えて、実際は「値が入っていれば危険側」に倒れる。本プロジェクトも同じ構成のため適用する（Issue #168）。

## 本プロジェクトの前提（重要）

**開発用の Supabase 環境は存在しない。Supabase プロジェクトは本番の 1 つだけである。**

一般的な本番データ保護ルールは「書き換えを伴う作業は非本番環境で行う」と定めるが、**本プロジェクトにはその代替先が Testcontainers の使い捨て Postgres しかない**。したがって:

| 用途 | 使う環境 |
|---|---|
| ローカル開発・IT | **Testcontainers の使い捨て Postgres**（`pnpm test:integration` が起動する）。接続先ガードは `testing.md` を参照 |
| E2E | `NEXT_PUBLIC_AUTH_MODE=local` / `NEXT_PUBLIC_DATA_MODE=local` の localStorage モード。**DB に接続しない** |
| 動作確認・データを伴う検証 | **専用環境が無い。** 本番 Supabase を書き換えて代替しない |

- **「非本番環境で試す」が選べない場面では、その作業を実行しないことを既定とする。** 環境が無いことを、本番を触ってよい理由にしない。
- 検証用の環境が必要になった場合は、**本番を書き換える前に環境を用意することを提案する**（Supabase の別プロジェクト / ブランチ機能 / `supabase start` によるローカルスタック）。判断はユーザーが行う。

## 原則

- **本番 DB は書き換えない。** 検証・調査・データ操作を伴う作業は本番以外で行う。「本番でしか再現しない」と判断する前に、Testcontainers での再現を試みる。
- **本番 DB への書き込みは、アプリケーションコード経由（Route Handlers → Prisma）に限る。** 手元からの実行・手打ち SQL・管理コンソールを通常運用に組み込まない。
- **マイグレーションによる本番適用の経路は存在しない。** 本プロジェクトは `prisma migrate` を禁止し（`database.md`）、DB 側のスキーマ変更は別プロジェクトで管理している。**アプリ側から本番へスキーマを適用する正規の手段は無い**ため、「マイグレーションなら安全」という例外を作らない。スキーマ変更が必要なら DB 側の管理者に依頼する。
- **接続先は毎回明示的に確認する。** 「たぶんローカルを向いている」で破壊的操作を実行しない。実行前に接続先ホストを出力して確認する。
- **既定は read-only。** 書き込みは必要な操作の直前にだけ行う。参照目的の接続で書き込み可能な資格情報を使わない。
- **本番の接続情報をローカルの既定環境変数に常駐させない。** `front/.env.local` の `DATABASE_URL` は本番を指す。**テスト・スクリプトがこれを暗黙に拾わないようにする**（事故の直接原因。`testing.md` を参照）。
- **復旧手段を先に確認する。** バックアップ / PITR が有効で、直近の復旧ポイントが分かっている状態でのみ、書き換えを伴う操作を許可する。

## 禁止する操作（本番接続先に対して）

- スキーマの破壊的再作成・リセット（`prisma migrate reset` / `prisma db push` / `prisma migrate dev`）
- `TRUNCATE` / `DROP` / 条件なしの `DELETE` / 条件なしの一括 `UPDATE`
- **テスト・シードスクリプトの実行**（seed は既存データを `deleteMany()` で削除する前提で書かれていることが多い。本ルールの起点となった事故がこれ）
- マイグレーションファイルを介さない、コンソール・CLI での直接スキーマ変更

これらが必要になった場合は、後述の「例外手順」を通す。ルールを黙って迂回しない。

### 機械的ガード（Prisma CLI）

上記のうち Prisma CLI 経由のものは **`front/scripts/prisma-guard.ts` が実行前に拒否する**（Issue #178）。`prisma.config.ts` が全サブコマンドで読み込まれる性質を利用し、設定を解決する前に落とす。

**対象サブコマンドと許可ホストの一覧は、実際に実行されるコードを正とする**（`scripts/prisma-guard.ts` の `DESTRUCTIVE_COMMANDS` と `scripts/db-host-allowlist.ts` の `ALLOWED_DB_HOSTS`）。本ルールに再掲すると、片方だけ変わったときに「ルールには書いてあるが実装されていない」状態になる。ここには**そう設計した理由**だけを残す。

- **判定軸はコマンド名ではなく接続先。** 禁止したいのは「本番を壊すこと」であって「コマンドそのもの」ではない。コマンド名だけで拒否すると、将来ローカル DB や開発用環境を用意したときに正当な操作まで塞がれ、**その手間がガードを外す動機になる**。
- **解除用の環境変数は用意していない。** 唯一の緩和手段は allowlist へのホスト追加で、これは**PR に残るレビュー対象の変更**になる。環境変数による解除は痕跡が残らず、「エラー回避のために解除する」を招く。
- **DB を壊さないサブコマンドは本番接続先でも通す**（`db pull` によるスキーマ取得など、正当な用途を塞がないため）。
- **未知のサブコマンドは拒否しない。** 過剰に塞ぐとガードごと外されやすく、それが最悪の結果になる。既知の危険操作を確実に止めることに絞り、**網羅性は本ルールが担保する**（Prisma に破壊的コマンドが追加された場合はコード側の追随が必要）。

## AI エージェント（Claude Code / Codex / MCP）に対する制約

自動化されたエージェントは**接続先を確認せずに操作を完了できてしまう**ため、人間より強い制約を課す。**本プロジェクトは Supabase MCP が接続されており、エージェントから本番 DB を直接操作できる状態にある**ことを前提に読むこと。

- **本番プロジェクトに対する MCP の書き込み系ツール（`execute_sql` の DML/DDL・`apply_migration` 等）を実行しない。** 参照系（`list_tables` / `get_logs` / `get_advisors` / `list_migrations`）に留める。
- **上記の前提どおり、書き込みを振り替える先が無い。** 「非本番環境でやります」と言えないため、書き込みが必要になった時点で**止まってユーザーに報告する**。
- それでも本番への書き込みが避けられない場合は、**実行前に「接続先（プロジェクト名）」と「実行する SQL」を提示し、ユーザーの明示承認を得る。** 承認は 1 操作ごとに取り、以前の承認を次の操作に流用しない。
- **エラーの回避策として接続先を変更しない。** 「テスト DB に繋がらないから本番を使う」「環境変数を手で書き換えて通す」は禁止。原因を報告して止まる。
- **`.env.local` を読んで得た接続情報を、スクリプトやテストの実行に転用しない。**

## 例外手順（本番データの修正が避けられない場合の最終手段）

0. **Testcontainers で代替できないことを確認する**（できるなら本番を対象にしない）。そのうえで、同じ操作を Testcontainers 上で先に実行し、結果を確かめる
1. 目的・影響範囲・対象件数を事前に書き出す（issue / PR に残す）
2. **dry-run を先に実行**し、対象件数と対象レコードを確認する
3. バックアップ / PITR の復旧ポイントを確認する
4. **冪等なスクリプト**として実装し、レビューを受ける（アドホックな手打ち SQL にしない）
5. 実行時は接続先を明示表示し、トランザクションで囲む。想定件数と乖離したらロールバックする
6. 実行結果（対象件数・所要時間・異常の有無）を記録に残す。事故・ヒヤリハットに至った場合は `lessons-learned.md` に従って教訓を残す

## DB 以外の本番リソース

同じ原則を、破壊・不可逆な副作用を持つ他の本番リソースにも適用する。

- Supabase Storage / オブジェクトストレージの削除・上書き
- Supabase Auth のユーザー削除・一括更新
- メール / 通知の一斉送信（宛先を本番ユーザーに向けた実行）
- キュー・ジョブの一括削除、外部 SaaS の一括更新

いずれも**接続先・宛先・キーの種別を allowlist で検証**し、本番を指していたら実行前に失敗させる。
