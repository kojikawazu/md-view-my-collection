## 2026-08-22 置き換え済みの旧手順が「正式一覧」の見出しで残り、本番 DB 破壊へ向かう手順書になっていた

### 概要

親 issue #142（コードとルールの乖離解消）は全サブ issue がクローズ済みだったが、完了条件のもう一方「既知の乖離が無い状態」を機械的に確かめ直したところ**新たに 5 件**見つかった。最も重かったのは `docs/07-api-specification.md` の自己矛盾で、置き換え済みの旧テスト方式が「**API 統合テスト（新規追加 / 正式一覧）**」という見出しのまま残り、その内容が「DB: テスト用 Supabase 実 DB」だった。

### 詳細

- 何が起きたか: 同じファイルの上部（288 行）に「旧案（実テスト用 Supabase プロジェクト + `tests/api/`）は Testcontainers 方式に置き換えた」と書きながら、下部（877 行〜）では旧案を「正式一覧」の見出しで提示し続けていた。他に、`AGENTS.md` が `components/AppStateProvider.tsx`（実際は `providers/`）を、`docs/10-miscellaneous-specification.md` が `components/ReportMarkdown.tsx`（実際は `components/organisms/`）を指し、`docs/07-api-specification.md` の見出しが分割済みの `front/src/types.ts` を指し、`environment.md` の環境変数一覧から `TEST_DATABASE_URL` と `PLAYWRIGHT_BASE_URL` が抜けていた。実害は出ていないが、`TEST_DATABASE_URL` は**本番 DB 破壊を防ぐガードの唯一の上書き手段**であり、一覧に無いことは把握漏れに直結する。
- なぜ起きたか（根本原因）: **ドキュメントの陳腐化は、実装が変わったときに参照側が変更セットから漏れる形で起きる。** #163（型の分割）・#164（schemas の移動）・IT の Testcontainers 化で実装は変わったが、それらのパスを参照していた仕様書は変更セットに含まれなかった。`documentation.md` の影響マップは「変更種別 → 更新必須ドキュメント」を引く表であり、「**そのパスを参照している他のドキュメント**」までは辿らない構造だった。加えて、旧記述を「経緯として残す」判断自体は妥当だが、**見出しが現行の手順に見える形**だったため、本文の但し書きが読み手に届かなかった。
- 教訓 / 次からどうする: **棚卸しは目視でなく機械的に回す。** 効いたのは 2 つで、(1) ドキュメント中のバッククォート付きファイルパスを全部抜き出して実在確認する、(2) コードの `process.env.*` と環境変数一覧を突き合わせる。目視レビューでは「書いてある内容が正しそうか」しか判定できず、参照先が実在するかは分からない。**ファイルを移動・改名したら、そのパスを参照している `.md` を `grep` して同じ変更セットで直す。** ただし**過去の作業記録（`[x]` の完了ログ・本ファイルの教訓）は直さない** — 当時の事実であり、書き換えると履歴が壊れる。そして**置き換えた旧手順を残すなら、見出しに「旧案」「置き換え済み」を入れる**。本文の但し書きだけに頼らない。
- 関連: [`../.claude/rules/documentation.md`](../.claude/rules/documentation.md)（本教訓を「ファイルを動かしたら参照している .md を直す」「乖離の棚卸しは機械的に回す」「置き換えた旧方式は旧案と見出しで明示する」として昇格済み）、[`../.claude/rules/production-data.md`](../.claude/rules/production-data.md)（旧手順が向かう先だった事故）、#142、#163、#164

## 2026-08-22 コンソールエラーを「描画できているから実害なし」と判断し、機能が壊れていることを見逃した

### 概要

Issue #166（CSP 強制化）の観測中に `/docs` で `TypeError` を見つけたが、「オペレーション一覧は描画されているので実害なし」と判断してスコープ外にした。実際には**オペレーションを展開すると中身が完全に空**で、API リファレンスとして機能していなかった。

### 詳細

- 何が起きたか: `swagger-ui-react` が OAS 3.1 を解決する際に `TypeError: refract is not a function` で失敗していた。エンドポイント一覧（8 オペレーション）は描画されるため一見正常に見えるが、展開すると Parameters / Request body / Responses が**一つも描画されない**（`.opblock-body` の `innerText` が空文字）。#166 の PR には「Swagger UI の描画自体は成功している」「CSP とは無関係の別件」と書き、**実害の有無を確認しないまま**別 issue（#197）へ送った。#197 で実際に展開して初めて、機能が壊れていると分かった。原因は `swagger-ui-react` がバンドラの解決を通る過程で apidom の interop が壊れることで、バンドラを通さない `swagger-ui-dist` の自己完結バンドルでは同じ spec が正しく描画される。
- なぜ起きたか（根本原因）: **「画面に何か出ている」を「機能している」の証拠として使った。** 見えていたのは一覧というトップレベルの描画だけで、エラーが起きていた `$ref` 解決の結果（スキーマ）は画面の一段深いところにあった。スタックトレースは `resolveSubtree`（サブツリーの解決）を指しており、「欠けるのはトップレベルではなく下位の描画だ」と読めば影響範囲を推測できたが、目視の印象を優先した。加えて、当時の関心は CSP にあり、「CSP と無関係」と切り分けた時点で調査を打ち切ってしまった。
- 教訓 / 次からどうする: **エラーを「実害なし」と判断するなら、実害が出るはずの操作まで実際にやってから言う。** 「表示されている」ではなく「その機能の目的を果たす操作」を試す（API リファレンスなら、オペレーションを展開してスキーマを読むところまで）。**スタックトレースの関数名を影響範囲の手がかりとして読む**（`resolveSubtree` の失敗は下位の描画が欠けることを示唆する）。確認しきれない場合は「実害なし」と言い切らず**「未確認」と明記して次に渡す**（#197 では未確認範囲を明記したため拾い直せた）。
- 関連: #166（見逃した側）、#197（修正）、[`08-test-specification.md`](08-test-specification.md)。同日の「アサーション順序」の教訓と**同じ構造**である — 「赤くなった＝検証できた」ではないのと同様に、「描画された＝機能している」でもない。**観測した事実と、そこから言える結論の距離を詰めずに飛ぶのが共通の失敗パターン。**

## 2026-08-22 セキュリティ観点のアサーションが、先頭の前提確認に隠れて一度も評価されていなかった

### 概要

E2E の TC-041（生 HTML のサニタイズ検証）は変異を与えると赤くなったが、落ちていたのは常に先頭の前提確認（見出しの表示）で、**本来の検証対象であるサニタイズのアサーションは一度も評価されていなかった**。同じ構造が E2E・IT の計 7 箇所にあり、認可（403）やバリデーション失敗時の非書き込みが同じ形で隠れていた。

### 詳細

- 何が起きたか: Issue #25 で追加した TC-041 をミューテーションテストで確かめた際に判明した。`ReportMarkdown` を壊す変異を 2 パターン与えたところ両方で赤くなったが、失敗はどちらも 1 番目の見出しアサーションで、2〜5 番目（`script` 非注入・`img[src="x"]` 非注入・`javascript:` リンク非注入・スクリプト未実行）は評価されていなかった。Markdown 描画は正常なまま生 HTML だけが通る 3 つ目の変異を作って、初めて 2 番目が機能することを確認できた。Issue #187 で全テストを点検した結果、同じ構造が E2E に 4 箇所（TC-041 / TC-004・005・006 / TC-020 / TC-009・010）、IT に 3 箇所（`requireAdmin` の 403・バリデーション失敗時に DB へ書き込まないこと・`is-allowed` の拒否側）見つかった。実害（誤って通っていたテスト）は無かったが、7 箇所が「テストがある」という安心感だけを生んでいた。
- なぜ起きたか（根本原因）: Vitest も Playwright も最初の `expect` 失敗でその test の実行を打ち切る。1 つの test に「前提確認」と「本来の検証対象」を同居させ、前提確認を先頭に置くと、**前提が壊れる変更と検証対象が壊れる変更が同じ原因で同時に起きたとき、検証対象は一度も実行されない**。「テストが存在する」「変異を与えたら赤くなった」はどちらも観点を検証できている証拠にならないのに、証拠として扱っていた。セキュリティ・認可の観点は壊れても画面が正常に見えるため、この穴が最も危険な形で残る。
- 教訓 / 次からどうする: **「赤くなったか」で止めず「どのアサーションで落ちたか」まで確認する。** 前提確認で落ちているなら、そのテストは本来の観点を検証できていない。是正はアサーションの**並べ替えでは効かない**（隠す側が入れ替わるだけ）ので、UT / IT は観点ごとに test を分割し、E2E は前提確認を `expect.soft()` にして検証対象を必ず評価させる。**前提確認を消して解決しない** — `toHaveCount(0)` 系は画面が描画されていなくても通るため、前提確認が無いと偽の緑になる。`異常: 未認証 401 / 非管理者 403` のように**テスト名が 2 つの観点を指しているものは分割対象の目印**として使える。
- 関連: [`../.claude/rules/testing.md`](../.claude/rules/testing.md)（本教訓を「アサーションの並べ方（前提確認で本命を隠さない）」として昇格済み）、[`08-test-specification.md`](08-test-specification.md)（是正箇所の記録）、#187（本点検）、#25（TC-041 の追加）

## 2026-08-08 既存 issue を検索せずに残課題を起票し、7 日前の issue と重複させた

### 概要

PR #170 の残課題を issue 化する際、既存の open issue を確認しないまま #172 を起票した。同じ内容が 1 週間前に #168 として起票済みで、しかも #168 の方が範囲が広く、実際に起きた本番データ全削除事故という起票理由まで持っていた。#172 は即クローズし、内容を #168 へ転記することになった。

### 詳細

- 何が起きたか: `production-data.md` の取り込みを #172 として起票したが、これは #168「本番 DB 破壊の再発防止」の部分集合だった。#168 には `production-data.md` の取り込みも、私が「ブロッカー」として新たに書き出した非本番 Supabase 環境の確認も、既に項目として含まれていた。実害は無かったが、起票 → 重複判明 → クローズ → 転記の往復が発生し、一時的に「同じ作業を指す open issue が 2 つある」状態を作った。
- なぜ起きたか（根本原因）: 直前の作業（upstream ルールの取り込み）の文脈だけで「これは新しい残課題だ」と判断し、リポジトリ全体の状態を確認しなかった。`gh issue create` は重複を検知しないため、検索を挟まなければ必ず通ってしまう。加えて `github-issue.md` は起票のタイミング（ブランチと対）と粒度（1 issue = 1 PR）は定めていたが、**起票前の重複確認を求めていなかった**ため、手順としても抜けていた。会話の文脈内で完結する判断ほど、リポジトリ側の既存状態と突き合わせる動機が働かない。
- 教訓 / 次からどうする: **`gh issue create` の前に必ず `gh issue list --state open` で全件のタイトルを見る**（キーワード検索だけに頼らない。#168 のタイトルは「本番 DB 破壊の再発防止」で、`production-data` では引っかからなかった）。既存 issue と範囲が重なる場合は、新規起票ではなく**既存 issue へのコメント追記**を第一候補にする。範囲が広い方を残し、狭い方を閉じる。
- 関連: [`../.claude/rules/github-issue.md`](../.claude/rules/github-issue.md)（本教訓を「起票前の重複確認」として昇格済み）、#172（重複・クローズ済み）、#168（統合先）、#170（発端の PR）、#173（本エントリの記録）
