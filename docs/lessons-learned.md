## 2026-08-22 セキュリティ観点のアサーションが、先頭の前提確認に隠れて一度も評価されていなかった

### 概要

E2E の TC-041（生 HTML のサニタイズ検証）は変異を与えると赤くなったが、落ちていたのは常に先頭の前提確認（見出しの表示）で、**本来の検証対象であるサニタイズのアサーションは一度も評価されていなかった**。同じ構造が E2E・IT の計 7 箇所にあり、認可（403）やバリデーション失敗時の非書き込みが同じ形で隠れていた。

### 詳細

- 何が起きたか: Issue #25 で追加した TC-041 をミューテーションテストで確かめた際に判明した。`ReportMarkdown` を壊す変異を 2 パターン与えたところ両方で赤くなったが、失敗はどちらも 1 番目の見出しアサーションで、2〜5 番目（`script` 非注入・`img[src="x"]` 非注入・`javascript:` リンク非注入・スクリプト未実行）は評価されていなかった。Markdown 描画は正常なまま生 HTML だけが通る 3 つ目の変異を作って、初めて 2 番目が機能することを確認できた。Issue #187 で全テストを点検した結果、同じ構造が E2E に 4 箇所（TC-041 / TC-004・005・006 / TC-020 / TC-009・010）、IT に 3 箇所（`requireAdmin` の 403・バリデーション失敗時に DB へ書き込まないこと・`is-allowed` の拒否側）見つかった。実害（誤って通っていたテスト）は無かったが、7 箇所が「テストがある」という安心感だけを生んでいた。
- なぜ起きたか（根本原因）: Vitest も Playwright も最初の `expect` 失敗でその test の実行を打ち切る。1 つの test に「前提確認」と「本来の検証対象」を同居させ、前提確認を先頭に置くと、**前提が壊れる変更と検証対象が壊れる変更が同じ原因で同時に起きたとき、検証対象は一度も実行されない**。「テストが存在する」「変異を与えたら赤くなった」はどちらも観点を検証できている証拠にならないのに、証拠として扱っていた。セキュリティ・認可の観点は壊れても画面が正常に見えるため、この穴が最も危険な形で残る。
- 教訓 / 次からどうする: **「赤くなったか」で止めず「どのアサーションで落ちたか」まで確認する。** 前提確認で落ちているなら、そのテストは本来の観点を検証できていない。是正はアサーションの**並べ替えでは効かない**（隠す側が入れ替わるだけ）ので、UT / IT は観点ごとに test を分割し、E2E は前提確認を `expect.soft()` にして検証対象を必ず評価させる。**前提確認を消して解決しない** — `toHaveCount(0)` 系は画面が描画されていなくても通るため、前提確認が無いと偽の緑になる。`異常: 未認証 401 / 非管理者 403` のように**テスト名が 2 つの観点を指しているものは分割対象の目印**として使える。
- 関連: [`../.claude/rules/testing.md`](../.claude/rules/testing.md)（本教訓を「アサーションの並べ方（前提確認で本命を隠さない）」として昇格済み）、[`08-test-specification.md`](08-test-specification.md)（是正箇所の記録）、#187（本点検）、#25（TC-041 の追加）

## 2026-08-08 既存 issue を検索せずに残課題を起票し、7 日前の issue と重複させた

### 概要

PR #170 の残課題を issue 化する際、既存の open issue を確認しないまま #172 を起票した。同じ内容が 1 週間前に #168 として起票済みで、しかも #168 の方が範囲が広く、実際に起きた本番データ全削除事故という起票理由まで持っていた。#172 は即クローズし、内容を #168 へ転記することになった。

### 詳細

- 何が起きたか: `production-data.md` の取り込みを #172 として起票したが、これは #168「本番 DB 破壊の再発防止」の部分集合だった。#168 には `production-data.md` の取り込みも、私が「ブロッカー」として新たに書き出した非本番 Supabase 環境の確認も、既に項目として含まれていた。実害は無かったが、起票 → 重複判明 → クローズ → 転記の往復が発生し、一時的に「同じ作業を指す open issue が 2 つある」状態を作った。
- なぜ起きたか（根本原因）: 直前の作業（upstream ルールの取り込み）の文脈だけで「これは新しい残課題だ」と判断し、リポジトリ全体の状態を確認しなかった。`gh issue create` は重複を検知しないため、検索を挟まなければ必ず通ってしまう。加えて `github-issue.md` は起票のタイミング（ブランチと対）と粒度（1 issue = 1 PR）は定めていたが、**起票前の重複確認を求めていなかった**ため、手順としても抜けていた。会話の文脈内で完結する判断ほど、リポジトリ側の既存状態と突き合わせる動機が働かない。
- 教訓 / 次からどうする: **`gh issue create` の前に必ず `gh issue list --state open` で全件のタイトルを見る**（キーワード検索だけに頼らない。#168 のタイトルは「本番 DB 破壊の再発防止」で、`production-data` では引っかからなかった）。既存 issue と範囲が重なる場合は、新規起票ではなく**既存 issue へのコメント追記**を第一候補にする。範囲が広い方を残し、狭い方を閉じる。
- 関連: [`../.claude/rules/github-issue.md`](../.claude/rules/github-issue.md)（本教訓を「起票前の重複確認」として昇格済み）、#172（重複・クローズ済み）、#168（統合先）、#170（発端の PR）、#173（本エントリの記録）
